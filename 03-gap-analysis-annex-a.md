## Gap Analysis

### A.6 People Controls

| Control | Control Name | Finding Reference | Rating | Justification |
|---|---|---|---|---|
| A.6.1 | Screening | Background checks conducted on new hires | Partial | A screening step exists (background checks), which satisfies part of A.6.1's intent. However, there's no evidence screening is applied consistently across all roles, documented as a formal policy, or repeated/reviewed on an ongoing basis (e.g., for role changes or periodic re-verification). Rated Partial rather than Implemented because a control existing informally isn't the same as it being defined and managed. |
| A.6.3 | Information security awareness, education and training | No formal onboarding walkthrough of security responsibilities; no awareness training program described | Not Started | No evidence of either component this control requires: no structured onboarding communication of security responsibilities, and no ongoing awareness training program (e.g., phishing simulation, annual training) described anywhere in current practice. Unlike A.6.1, there's no partial mechanism to point to — this is a full gap. |
| A.6.5 | Responsibilities after termination or change of employment | No offboarding checklist; no confirmed access revocation process | Not Started | No documented offboarding process exists, and there is a confirmed real-world failure (a departed employee's shared-login access was never revoked) — this isn't a theoretical gap, it's an evidenced one. This mirrors the PR.AA-01 finding from the CSF exercise, reinforcing that identity lifecycle management is a systemic weakness across frameworks, not a one-off. |

### A.5 Organizational Controls

| Control | Control Name | Finding Reference | Rating | Justification |
|---|---|---|---|---|
| A.5.1 | Policies for information security | No formal information security policy exists | Not Started | There is no written policy of any kind governing information security. Decisions are made informally by one engineer, which is a person acting as a control, not a documented, repeatable policy — this distinction matters because the control is asking whether direction exists independent of any one individual. |
| A.5.2 | Information security roles and responsibilities | No defined roles/responsibilities structure | Not Started | No formal ownership structure exists. One engineer has informally absorbed security tasks alongside their primary role, but there's no defined authority, accountability, or backup if that person leaves — a single point of failure rather than a managed responsibility structure. |
| A.5.15 | Access control | Ad hoc access provisioning, no least-privilege standard | Not Started | Directly reinforced by the A.6.5 and prior PR.AA-01 findings — access is granted informally with no defined standard, and no process exists to remove it either. No partial mechanism observed to justify a higher rating. |
| A.5.18 | Access rights | No documented access rights review process | Not Started | Same root cause as A.5.15 — without a policy defining who *should* have access, there's nothing to periodically review or reconcile against. This rates independently low rather than inheriting A.5.15's rating automatically, but the evidence points the same direction. |
| A.5.19–A.5.22 | Supplier relationships | No formal vendor/supplier security review process | Not Started | No evidence of a supplier risk assessment process, despite Northbridge's material dependency on AWS and Okta as critical infrastructure. This is a notable gap given how much of Northbridge's security posture is actually inherited from these vendors rather than built in-house. |
| A.5.24 | Incident management planning and preparation | No written incident response procedure | Not Started | No incident response plan exists in any form. This finding is elevated in severity because it was already identified by an external party (the prior vendor security review) 8 months ago and has not been actioned — this is a repeat, acknowledged gap, not a newly discovered one. |
| A.5.26 | Response to information security incidents | No defined incident response process | Not Started | Directly dependent on A.5.24 — without a documented plan, there's no defined response process to execute. Rated the same for consistency, since one control's absence structurally causes the other's. |

### A.8 Technological Controls

| Control | Control Name | Finding Reference | Rating | Justification |
|---|---|---|---|---|
| A.8.1 | User endpoint devices | Mixed personal/company laptops, no described device management policy | Not Started | No mobile device management (MDM), endpoint security standard, or policy distinguishing acceptable use of personal vs. company devices. Elevated concern for a remote-first company, since endpoints are the primary access point to in-scope systems outside any office environment. |
| A.8.2 | Privileged access rights | Standalone logins on legacy tools outside Okta | Partial | Rated Partial rather than Not Started because Okta SSO *does* provide some centralized, presumably more secure access control for most systems — the gap is specifically the legacy tools sitting outside that coverage, not a total absence of the control. |
| A.8.5 | Secure authentication | Okta SSO deployed for most, not all, internal tools | Partial | Same reasoning as A.8.2 — meaningful authentication infrastructure exists and is in active use, but coverage is inconsistent. The legacy tools represent the actual gap, not the authentication approach itself. |
| A.8.9 | Configuration management | No information on secure configuration baselines for cloud infrastructure | Unable to Assess | Terraform is in use, which *could* support configuration-as-code baselines, but there's no evidence confirming whether baselines are actually defined, reviewed, or enforced. This needs direct technical verification (e.g., reviewing Terraform modules/policies) rather than an assumption either way. |
| A.8.15 | Logging | No described logging capability | Unable to Assess | No information available on what is or isn't logged. Flagged for technical follow-up rather than assumed Not Started, since AWS provides logging capability by default (e.g., CloudTrail) that may exist without anyone having configured monitoring on top of it — an important distinction to verify, not guess at. |
| A.8.16 | Monitoring activities | Company cannot confirm whether it has experienced a security incident | Not Started | Unlike A.8.15 (logging may passively exist), this rates lower because the finding directly states an *inability to detect* — "they think nothing happened" is explicit evidence of no active monitoring or alerting capability, not just an unknown. |
| A.8.25 | Secure development life cycle | No information on code review enforcement or SDLC practices | Unable to Assess | GitHub and CI/CD pipeline existing doesn't confirm secure development practices are enforced within them (e.g., mandatory PR review, branch protection, static analysis). Requires direct verification of pipeline configuration rather than inference from tooling choice alone. |
| A.8.28 | Secure coding | No information on secure coding standards or practices | Unable to Assess | Same reasoning as A.8.25 — tooling presence (GitHub Actions) doesn't confirm secure coding standards are actually defined or enforced; this is a scoping question for a technical interview with engineering leadership, not an assumption. |
